# Iteration 2 decisions and scope

**Candidate:** `blue-rooted-checkpoint/1.0-draft.2`. Implementation-target specification; not a deployed profile or a certified RC.

## Preserved user requirement

One selected root and its forward declared embedded graph define the calculation. The driver takes the earliest pending eligible input from each exact view's existing progress. `PROCESS(document, input)` finishes that one input. Old newly embedded views do not reset existing checkpoints; unrelated reverse observers do not enlarge root scope. A missing local handler is not permission to discard reference advancement or descendant delivery.

## Preserved draft.1 candidate choice

One LIVE rooted calculation has one shared logical meter and one atomic owned result. The revision does **not** silently switch to SCC-only operation evaluation or own-work-only gas. An independent consumer does not contribute sibling work. Reuse preserves the selected root reference trace, including tight-budget failure. The selector proof establishes neither tariff nor publication policy.

## Explicitly completed in this iteration

1. **Owned versus root-local results:** entry owners are the selected root's current live SCC. Forward dependencies outside it remain selected local views unless authenticated live joins or provisional births expand ownership. Source-first/parent-first/cache/failure schedules have a normative outcome table. A parent's calculated child value is not the independent child's authoritative publication. An independent source may later verify/reuse the computation in its own operation.
2. **Cause-kind selection:** a historical interval is fixed from the attachment's logical join anchor, not a worker's current cache head. A root already live for an external entry remains a LIVE calculation even after independent source execution. Old required applications are not skipped. These are candidate completion rules, not a claim that the previous implementation already followed them.
3. **Closed identities:** exact history-basis/admission records and a canonical entry SCC owner replace the ambiguous draft.1 context. A/B public views in the same live group share one operation anchor; actual different requests remain different causes. Entry identity and meter remain frozen over merges/splits. New draft.2 domains prevent collision with earlier prototypes.
4. **Qualification:** recipe-only obligations cannot receive a production PASS from the supplied runner. The nine literal critical cases require complete named variants, exact step evidence, positive anchors, real before/after records, restart, gas arithmetic/boundaries and independently pinned artifact/dependency bytes. The remaining cases stay explicit adapter/fixture obligations.

These decisions preserve Blue value/identity algorithms, BEX operator semantics, gas weights and portable numeric limits. They do not imply that cold/warm reuse can omit semantic work or that a transient child projection can overwrite a source head.

## Verification boundary

The package supplies exact normative text, wrapper vectors, a finite ownership model and a stronger test driver. It does not implement the revised Java processor, a full MyOS adapter or the external-state POC. All 34 production scenarios remain NOT_RUN. The nine literal plans remove setup/oracle ambiguity for critical cases; they are not nine production test passes. Base BlueId/receipt authenticity and exact production work-count oracles remain responsibilities of the maintained real implementation and its conformance suite.
