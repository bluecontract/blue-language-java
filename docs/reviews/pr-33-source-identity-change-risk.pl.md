# PR #33: zakres i ryzyko zmiany kanonizacji Source

Analiza z 2026-09-11. Kod: `036540104715e0841392a6f5055232a95b134802`, baza: `4128fb190b9f92fa6aa094ebba11803f312cd9fd`. Dotyczy [PR #33](https://github.com/bluecontract/blue-language-java/pull/33), [komentarza P1](https://github.com/bluecontract/blue-language-java/pull/33#discussion_r3976482299) oraz [issue #24](https://github.com/bluecontract/development/issues/24).

**Ocena: wysokie ryzyko semantyczne i kompatybilności.** Wcześniejsza propozycja kanonizowania zmaterializowanej referencji tak samo jak jej zawartości inline jest kierunkiem do zbadania, ale nie jest kompletnym algorytmem. Dodanie pochodzenia danych do kanonizatora nie rozwiązuje przypadku, w którym referencji w ogóle nie otwarto. Nie ma jeszcze implementacji przechodzącej wszystkie potrzebne regresje.

**Co potwierdzono wykonaniem kodu**

Pierwsza seria obejmowała 11 porównań na PR i bazie. Na PR cztery dawały różne Source ID przy równych dokładnych materiałach inline/reference i akceptacji obu form: obiekt bez typu pod polem z typem niestandardowym, raw Text/Currency, raw Amount pod typowanym polem oraz element listy bez typu przy niestandardowym `itemType`. Pierwsze dwa są nowymi regresjami; dwa kolejne istniały na bazie. Cztery testy dodane w PR przechodzą. Oba kontrolne warianty Amount, publikowane w postaci kanonicznej albo z jawnym Currency, przechodzą na PR.

W tej analizie dodano dwa przypadki raw Amount: pole bez zadeklarowanego typu oraz cały dokument jako inline albo czysta referencja. Oba mają równe dokładne ID i pełne rozwinięcia, ale różne Source ID na PR. Na bazie oba dawały równe Source ID. Referencje w tych dwóch przypadkach pozostają nieprzetworzone w resolved; nie należy rozszerzać wcześniejszej obserwacji identycznych resolved na te nowe przypadki. Akceptacja czystej referencji nie jest certyfikatem pełnej walidacji jej celu.

Dla root Amount dokładny ID oraz Source ID referencji to `57tBJW7XorkmHJ45Nw3RijtceKkbCRoQX5NmsxvhKt9D`; Source ID zawartości inline to `41dWQuZAqaQrwTstaM3pKBMdVNYzHm8GwXasKN6xz6vn`. Zatem obsługa wyłącznie referencji już otwartych przez resolver pozostawia ten przypadek bez poprawy.

Próby uproszczonych zmian poza repozytorium dały konkretne ostrzeżenia: warunkowe przywracanie referencji na podstawie ID zrekonstruowanego dziecka zepsuło 3/4 obecnych testów PR; wariant oparty na jawnie podanym typie zepsuł 2/4, w tym cold reload i zgodność skróconej składni skalara. Nie są to wyniki pełnej, proponowanej implementacji.

**Decyzja konieczna przed zmianą kodu**

[BlueLanguageRuntime.canonicalizeWithEvidence](../../blue-language-core/src/main/java/blue/language/runtime/BlueLanguageRuntime.java#L609) zwraca dla czystej referencji jej własny ID bez pobierania celu. [DefinitionReferenceValidationTest](../../blue-language-core/src/test/java/blue/language/runtime/DefinitionReferenceValidationTest.java#L14) jawnie wymaga braku pobrań. Jednocześnie Source-kanonizacja inline może przekształcić raw Amount, a więc nadać mu inne ID niż jego bezpośredni dokładny ID.

Nie można równocześnie zachować wszystkich trzech reguł dla dowolnej takiej wartości: referencja zawsze zwraca swój ID bez pobrania; inline podlega zmieniającej ID kanonizacji Source; obie formy zawsze mają ten sam Source ID. To konflikt zakresu kontraktów, a nie dowód, że istniejący szybki przypadek root-reference należy po prostu usunąć.

Specyfikacja musi rozstrzygnąć stosunek równoważności reprezentacji (§3.2 i §7.3), kanonizacji (§13.2), zachowania oryginalnych referencji (§13.4 i §13.5.1(4)) oraz przetwarzania dokładnego Content jako Source. Kanoniczny input nie zawsze jest poprawnym Source (§13.2), szczególnie dla końcowych payloadów list. Dlatego ponowne uruchomienie Source-resolvera na każdej pobranej treści byłoby niewystarczającą i ryzykowną regułą.

Wariant ograniczony do typowanych, wymagających rozwiązania wystąpień musi jawnie określić swój zakres i politykę dla pozostałych raw referencji. Wariant zapewniający pełną równoważność raw inline/reference wymaga decyzji o nowych pobraniach i zachowaniu root-reference, albo o spójnych zasadach dopuszczania danych. Odrzucanie raw danych również jest zmianą kompatybilności; nie jest automatycznie bezpieczniejszym patchem. Sam obowiązek publikowania wartości po kanonizacji nie zamyka issue, dopóki dotychczasowe raw wejścia nadal są akceptowane niespójnie.

**Potencjalne zmiany w kodzie**

1. **Pobieranie i pochodzenie wartości.** [ReferenceResolver](../../blue-language-core/src/main/java/blue/language/merge/ReferenceResolver.java#L343), [ResolutionEngine](../../blue-language-core/src/main/java/blue/language/merge/ResolutionEngine.java#L223) i [ResolutionSession](../../blue-language-core/src/main/java/blue/language/merge/ResolutionSession.java#L8). Zachować zweryfikowaną dokładną treść przed zastosowaniem kontekstu oraz powiązanie z konkretnym wystąpieniem w grafie danej operacji. Uwzględnić istniejące cache hits, zagnieżdżone rozwiązywanie i cyclic members. ID wartości nie wystarcza jako klucz kontekstu: ta sama wartość może wystąpić pod Text i Currency. Sam tekst ścieżki też nie wystarczy po patchu lub przesunięciu pozycji listy. Dowody muszą należeć do określonego grafu i przebiegu. Nowe dane nie powinny mutować caller-owned Node ani tworzyć globalnego stanu.

2. **Transport dowodów.** [TypeEvidenceResolution](../../blue-language-core/src/main/java/blue/language/merge/TypeEvidenceResolution.java#L20), [SnapshotResolution](../../blue-language-core/src/main/java/blue/language/merge/SnapshotResolution.java#L12), [ResolutionSnapshotFactory](../../blue-language-core/src/main/java/blue/language/merge/ResolutionSnapshotFactory.java#L24) oraz ścieżka `BlueLanguageRuntime.canonicalizeWithEvidence`. Obecna główna ścieżka Source korzysta z `resolveTypeDeclarationEvidence`; zmiana samej fabryki snapshotów ominęłaby ją. Potrzebny jest spójny transport dowodów wartości obok istniejących dowodów typów. To propozycja rozszerzenia modelu danych, nie gotowa nazwa nowej klasy. Nie należy bezrefleksyjnie dokładać kontekstu wartości do indeksu tożsamości typów.

3. **Rekonstrukcja kanoniczna.** [CanonicalIdentityInputBuilder](../../blue-language-core/src/main/java/blue/language/identity/CanonicalIdentityInputBuilder.java#L33) i [CanonicalIdentityInputReconstructor](../../blue-language-core/src/main/java/blue/language/identity/CanonicalIdentityInputReconstructor.java#L127). Zastąpić bezwarunkowe odtworzenie oryginalnej referencji regułą opartą na wybranym kontrakcie i zweryfikowanym pochodzeniu wkładu. Inline i otwarta referencja powinny używać tego samego kontekstu i rekonstrukcji, z zachowaniem label/schema/fixed-value provenance. Równość z ID oryginalnej referencji można oceniać dopiero na poprawnej postaci kanonicznej, nigdy przez bezpośredni hash resolved. Nie wolno automatycznie zastosować nowej reguły referencji wartości do pozycji `type`, referencji schema czy Contracts. [CanonicalTypeIdentityRecorder](../../blue-language-core/src/main/java/blue/language/merge/CanonicalTypeIdentityRecorder.java#L28) używa tego samego buildera do obliczania ID typów inline: wpływ może objąć także typy i ich użytkowników.

4. **Listy i mapowanie wystąpień.** [ListOverlayMerger.resolveListChild](../../blue-language-core/src/main/java/blue/language/merge/ListOverlayMerger.java#L381) oraz `reconstructItems`/`sourceItem` w rekonstruktorze. Kontekst `itemType` jest nakładany inaczej na referencję i na element bez typu. `$previous`, `$pos` i `$replace` wymagają powiązania finalnego elementu z poprawnym źródłem; indeks w ostatecznej liście nie zawsze odpowiada indeksowi w Source. Surowy list-item z wcześniejszego testu wymaga osobnego objęcia nową regułą, nie tylko zmiany `reconstructProperties`.

5. **Snapshoty i wejście Source/exact.** [ResolvedSnapshot](../../blue-language-core/src/main/java/blue/language/merge/ResolvedSnapshot.java#L247): audyt `fromSourceResolverResult`, `withSource`, `withCanonicalTypeIdentities`, `withCanonicalIdentityEvidence`, `toCanonicalBacked`, `toStrictBlueIdValidatedCanonical` i usuwania provenance referencji. Snapshot obecnie sprawdza parę przez ponowną rekonstrukcję z canonicalRoot użytym jako drugi argument buildera. Nowy algorytm musi zachować tę gwarancję spójności albo zastąpić ją równoważnym sprawdzeniem prawdziwego wejścia i dowodów. Nie można tylko usunąć wyjątku. Dokładny snapshot załadowany lub zmieniony patchem nie powinien być po cichu ponownie interpretowany jako authored Source. Zachowanie nowych dowodów przy `toCanonicalBacked` jest osobną decyzją dotyczącą pamięci i odtwarzania.

6. **Cache.** [ResolvedReferenceCache](../../blue-language-core/src/main/java/blue/language/merge/ResolvedReferenceCache.java#L444), `VerifiedReferenceResolution`, `VerifiedReferenceEntry`, `LanguageRuntimeSnapshotStore`. Współdzielony cache pod X musi nadal opisywać dokładną wartość X i jej niezależne rozwiązywanie. Wynik zastosowania kontekstu rodzica nie może zostać opublikowany pod X jako ogólna odpowiedź. Preferowany pierwszy wariant implementacyjny to dowody wystąpień wewnątrz operacji/snapshotu i współdzielenie niezmiennych dokładnych poddrzew. Globalny cache kontekstowy wymagałby osobnego uzasadnienia i pełnego klucza. Trzeba zachować pin/fork/commit/discard, generacje, ograniczenia pamięci i neutralność kolejności rozgrzewania cache.

7. **Minimalizacja.** [MinimizedOverlayBuilder](../../blue-language-core/src/main/java/blue/language/resolve/MinimizedOverlayBuilder.java#L35) przyjmuje obecnie tylko resolved oraz dowody typów. Jeśli docelowa tożsamość zależy od rozróżnienia dokładnego wkładu i wyniku kontekstowego, ten interfejs może wymagać również kanonicznego celu lub dowodów wartości. Usuwanie typu i collapse do starego X musi zachować Source ID po cold reload. Nie należy robić pełnego resolve/hash osobno dla każdej rozważanej redukcji: to może zwielokrotnić koszt. Potrzebne są jawne reguły zachowania wkładu i test całego cyklu.

8. **Consumers Contracts.** [WorkingDocument.snapshot](../../blue-contracts-core/src/main/java/blue/language/processor/WorkingDocument.java#L490), [CanonicalIdentityEvidence.projectResolvedGraph](../../blue-contracts-core/src/main/java/blue/language/processor/CanonicalIdentityEvidence.java#L483), [ProcessingDocumentView.capturePreInitializationScopeDocument](../../blue-contracts-core/src/main/java/blue/language/processor/ProcessingDocumentView.java#L521), `ProcessingSnapshotEvidence`, `ProcessingSnapshotTransaction`, `ExecutableBodyPathCatalog`. Te miejsca tworzą lub rekonstruują snapshoty i projekcje; obecnie przenoszą dowody typów. Nowe wymagania buildera muszą być dostępne także tutaj. Po patchu dowody starego wystąpienia mogą być nieaktualne. Efektem błędu mogłyby być zmienione ID capture/lifecycle/checkpoint albo niewłaściwy zakres pobrań. To zidentyfikowane miejsca audytu i potencjalnej adaptacji, nie stwierdzenie, że wszystkie wymagają zmiany logiki biznesowej.

9. **Interfejsy, Mini i wydanie.** Publiczne klasy buildera i snapshotów mają baseline API. Zachować zgodność binarną istniejących sygnatur, jeśli to możliwe; nowy overload nie może oznaczać, że stary i nowy wyliczają różne ID dla tego samego obsługiwanego wejścia. API Mini wymaga regresji obejmującej POST Content, GET dokładnej treści i Inspect z oboma ID oraz statusem konformancji. Audyt może wykazać potrzebę adaptacji mapowania błędów; samo różnicowanie Content/Source w API należy zachować. Zmiana normatywna wymaga aktualizacji specyfikacji, fixture'ów i powiązanych tożsamości pakietów zgodnie z procesem repozytorium, bez przepisywania baseline'ów wyłącznie po to, by testy przeszły.

**Ocena ryzyk i ich ograniczenie**

- **Wysokie — kontrakt Source/reference.** Brak decyzji o root i referencjach nieotwartych pozostawia lukę funkcjonalną. Dowód: dwa nowe reproduktory oraz test zakazujący pobierania root-reference. Ograniczenie: najpierw zapisać spójny zakres dopuszczania, canonicalization i provider demand dla root, pola, listy i zagnieżdżenia.
- **Wysokie — kompatybilność tożsamości.** Source ID części istniejących dokumentów i typów mogą się zmienić; zmiana ID dziecka przenosi się na rodziców. Dokładny Content ID niezmienionej treści pozostaje stabilny, jeśli bezpośredni algorytm i exact-load path pozostaną bez zmian. Ograniczenie: porównanie starej i nowej wersji na reprezentatywnych zapisanych dokumentach, przypięcie wersji semantyki do odtwarzania i jawny opis zgodności wydania.
- **Wysokie — zależność od cache.** Wynik kontekstowy pod kluczem X może wpłynąć na inne użycie X. To ryzyko projektowanej zmiany, nie potwierdzony obecny błąd cache. Ograniczenie: rozdzielenie dowodu dokładnej treści i dowodu wystąpienia; test jednej referencji w różnych kontekstach, obu kolejności, cache off/cold/warm/evicted/forked.
- **Wysokie — snapshot i provenance.** Utrata wkładu autora lub stare dowody po patchu mogą dać inne ID albo wyjątek spójności. Ograniczenie: pełny transport dowodów, sprawdzanie pochodzenia, Source/exact separation, round-trip snapshotów i lifecycle/capture regresje. Uproszczony eksperyment już pokazał realne błędy tej klasy.
- **Wysokie — koszt i dostępność przy rozszerzeniu pobrań.** Czyste referencje dziś mogą działać bez providera. Dodatkowe pobrania zwiększą zakres zależności od NOT_FOUND/UNAVAILABLE oraz koszt szerokich grafów; skali spowolnienia nie zmierzono. Dowody wymagają także limitów pamięci. Ograniczenie: jawny demand plan, zachowanie statusów i limitów, pomiar głębokich/szerokich grafów, cache accounting i niezmienność logicznego gas względem cache.
- **Średnie–wysokie — listy, schema, labels i cyclic sets.** Nietrafne powiązanie pochodzenia z pozycją, zgubienie jawnej etykiety lub samodzielne hashowanie członka cyklicznego może naruszyć tożsamość. Ograniczenie: osobne fixture'y `$pos`/`$replace`/prefix, fixed payload, labels równe odziedziczonym, schema refs, puste obiekty/listy i pełny dowód cyclic set.
- **Średnie–wysokie — interfejs publiczny i consumers.** Builder jest współdzielony przez Language i Contracts; stare konstruktory nie mają nowych danych. Ograniczenie: inwentaryzacja wszystkich tworzeń snapshotów, kompilacja consumers, baseline API i semantyczna zgodność przeciążeń. Nie ma podstaw do obietnicy, że zmiana pozostanie tylko wewnętrzna.

**Proponowana kolejność prac**

Najpierw utrwalić 13 scenariuszy jako testy z rozdzielonym `publishExact` i `publishCanonical`, a następnie rozstrzygnąć kontrakt root/unconstrained/typed oraz semantykę raw referencji. W tym kroku również sprawdzić, czy wejścia nadal mają być akceptowane; zamiana oczekiwanej równości na obserwowaną nierówność nie jest rozwiązaniem.

Potem przygotować niewielki eksperyment obejmujący jeden scalar i jeden raw Amount, ale od razu przez rzeczywistą ścieżkę Source, snapshot i cold reload. Dopiero po jego przejściu rozszerzyć dowody na listy, pozostałe snapshot factories, cache i Contracts. Transport dowodów można rozwijać przy niezmienionych wynikach, lecz przełączenie semantyki powinno być spójne: nie zostawiać starych ścieżek produkujących inne ID w tej samej wersji.

Po implementacji: celowane regresje, testy Language Core, pakietowe cykle i baseline API; następnie testy snapshot/cache/patch/fragmented/lifecycle w root i Contracts, exact conformance oraz wymagane weryfikacje wydania. Na końcu API Mini na przebudowanym, przypiętym runtime. Nie wykonywano pełnych suite'ów ani HTTP w ramach tej analizy i nie ma pomiaru wydajności przyszłej implementacji.
